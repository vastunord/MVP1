# Founder setup guide — Phase 02D

No production account or resource is connected. Complete these steps under **Vastu Nord's own vendor login**, not NRide or the Codex development account. Record project IDs and region privately; never paste secret values into Git, chat or documentation. Confirm current pricing and budget before activating any service.

1. **Account and project identity.** In GitHub, confirm this repository is `vastunord/MVP1`. In the Vastu Nord Vercel dashboard, confirm the signed-in team/account and create or select a dedicated web project rooted at `apps/web`. Keep Payload as a separate future project. Do not link this repository to an unrelated existing Vercel project or enable production auto-deployment without separate approval.
2. **Neon app database.** In the Vastu Nord Neon account, select region and retention with the founder, create a dedicated app project and isolated development/preview/production branches or projects. Keep the future Payload CMS database separate. Create scoped runtime and migration roles. Supply pooled runtime `DATABASE_URL` and direct migration `DIRECT_DATABASE_URL` only to their matching Vercel environment; never give the web app the CMS URL. Apply reviewed Prisma migrations to an isolated development database first, then verify a clean schema and restore procedure. No migration has been applied in Phase 02D.
3. **Vercel environment.** Set `APP_ENV` to `development`, `preview` or `production` matching Vercel's environment. Generate a unique random `BETTER_AUTH_SECRET` of at least 32 characters per environment. Set `BETTER_AUTH_URL` to the exact HTTPS production origin in Production; use the local origin for development, and verify preview callback/origin handling before enabling previews. Never prefix secrets with `NEXT_PUBLIC_`. Keep `MEDIA_UPLOADS_ENABLED=false` until private storage has passed its tests.
4. **Email delivery.** Approve a transactional sender and its cost. The current adapter expects a Vastu Nord-owned Resend account, verified sending domain, `AUTH_EMAIL_PROVIDER=resend`, `AUTH_EMAIL_FROM` and server-only `RESEND_API_KEY`. Send test verification and reset messages to controlled inboxes; check link expiry, one-time use, failed delivery and password-reset session revocation. Auth remains closed when these settings are absent. Production privacy/terms and retention text must be approved before customer registration.
5. **Optional Google sign-in.** In a Vastu Nord-owned Google Cloud project, configure the OAuth consent screen and a web client. Register exact authorized origins and callbacks such as `<origin>/api/auth/callback/google` for each approved environment. Supply `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` together, server-side, only after consent-screen and account identity review. Keep `GOOGLE_OAUTH_ENABLED=false` until callback, verified-email, denied-consent and same-email account-link tests pass; then explicitly set it to `true` in the approved environment. Without the flag and both values, the Google button stays hidden.
6. **Private media.** Select a dedicated private Vastu Nord Blob store per environment, verify region/cost/retention, then provide `BLOB_STORE_ID` and server-only `BLOB_READ_WRITE_TOKEN`. Test signed upload/download/expiry/ownership with synthetic images before enabling `MEDIA_UPLOADS_ENABLED=true`. The 727 Visuals files are unapproved and must not be uploaded or published by this setup.
7. **Acceptance checks.** With synthetic accounts on isolated resources, run signup → verification → sign-in → workspace → project create/rename/archive/restore/delete → sign-out/recovery; repeat with a second account and prove cross-user project/asset denial. Check DB role separation, audit events, rate limits, CSRF/origin protection, secret redaction and rollback. Only after these checks can authentication/persistence be called working in a connected environment.
